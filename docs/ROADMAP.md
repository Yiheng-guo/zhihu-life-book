# 实施顺序

## P0：先把产品讲清楚、走通、交付完整

1. 固定“大学篇”的四个主节点：入学、探索、大三准备、毕业。
2. 为每个选择补齐三件事：用户可能得到什么、需要付出什么、会带出什么问题。
3. 校验每个节点的因果承接：选择 → 回声 → 知乎来源 → 新问题 → 下一阶段；避免只有换文案、没有路径记忆。
4. 保留知乎来源类型、作者、摘要和独立原文链接；不把作者自述写成普遍规律。
5. 跑通静态体验和本地 API，处理来源未选、重复点击、过期会话、接口失败和刷新重来。
6. 锁定 3 分钟路演路径：开场问题 → 第一次选择 → 一条知乎来源 → 第二次选择 → 毕业分叉 → 今天的一步。
7. 补齐计划书、README、接口约定、比赛评分证据、部署地址和可回退版本。

## P1：再做一轮内容与交互打磨

8. 把长段落改成短句、标签和按需展开；每个画面只保留一个主要问题和一个主要动作。
9. 明确哪些是产品编排、哪些是知乎原文、哪些是产品编辑的问题与行动建议。
10. 用现场观众测试：20 秒能否理解产品，60 秒能否看见知乎结合，150 秒能否理解结局发散。

## P2：最后集中做视觉收口

11. 只保留一个封面方向和一个关键转场，集中制作高质量视觉冲击。
12. 再考虑轻量动效、声音、粒子或更复杂渲染；默认静音、可关闭、支持减少动态效果。
13. 视觉完成后只做一次公网发布与回归，不在每个小迭代都重复制作封面特效。

## Agent 判断

目前的“逐步选择、回声、来源、承接问题”是规则驱动的交互叙事，不是运行时 Agent。后续若接入一个 Agent，应让它解决具体问题：根据当前节点、选中的知乎内容和用户追问，检索有出处的内容，生成短解读和可执行尝试，再由后端做来源校验、缓存、去重和失败降级。多 Agent 只有在职责真的拆不开时再引入。
